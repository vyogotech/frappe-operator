# Comprehensive PostgreSQL Integration Guide

The `frappe-operator` provides first-class, production-ready support for PostgreSQL alongside MariaDB. You can deploy Frappe/ERPNext sites using either a **Shared** PostgreSQL cluster (ideal for multi-tenant SaaS) or a **Dedicated** per-site PostgreSQL instance (ideal for strict compliance requirements).

This integration leverages the robust [Percona Operator for PostgreSQL](https://github.com/percona/percona-postgresql-operator).

---

## 1. Quick Installation via Script

If you are installing the operator from scratch, the easiest way to get PostgreSQL support is to use the provided `install.sh` script with the PostgreSQL flag enabled.

```bash
# Downloads and installs the Frappe Operator along with Percona PostgreSQL Operator
INSTALL_POSTGRES_OPERATOR=true ./install.sh
```

This will automatically configure your Kubernetes cluster with the necessary Custom Resource Definitions (CRDs) required for PostgreSQL provisioning.

---

## 2. Deployment Modes

Just like MariaDB, you can configure your sites in two modes using `dbConfig.mode`. This can be set at the `FrappeBench` level (to apply to all sites on the bench) or overridden at the individual `FrappeSite` level.

### Shared Mode (`shared`) - Default & Recommended
Multiple `FrappeSite` resources share a single underlying `PerconaPGCluster`. 
- **Scalability**: $O(1)$ scaling overhead per site. You can run hundreds of sites on a single database cluster.
- **Automation**: The operator automatically provisions a unique database and a securely generated, least-privilege user for each site.

### Dedicated Mode (`dedicated`)
The operator spawns a brand new, physically isolated `PerconaPGCluster` strictly for the given `FrappeSite`.
- **Isolation**: Maximum data and resource isolation.
- **Overhead**: Requires more CPU and memory as a full PostgreSQL cluster is spun up for each site.

## 3. Step-by-Step Setup Guide

### Step 3.1: Pre-requisites (Manual Installation)

If you didn't use `INSTALL_POSTGRES_CRDS=true ./install.sh`, ensure the Percona Operator for PostgreSQL is installed in your cluster manually:

```bash
kubectl apply --server-side -f https://raw.githubusercontent.com/percona/percona-postgresql-operator/v2.3.1/deploy/bundle.yaml
```

### Step 3.2: Shared Cluster Provisioning

If you are using the default **Shared Mode**, you must first create a `PerconaPGCluster` that all your sites will connect to. We recommend naming it `frappe-postgres`.

```yaml
# frappe-postgres-cluster.yaml
apiVersion: pgv2.percona.com/v2
kind: PerconaPGCluster
metadata:
  name: frappe-postgres
  namespace: frappe-operator-system
spec:
  instances:
    - name: instance1
      replicas: 1 # Scale this up for HA
  proxy:
    pgBouncer:
      replicas: 1 # PgBouncer is used for connection pooling
```

Because `frappe-operator` needs to provision databases and roles *inside* this cluster for each new site, you must provide it with the cluster's superuser credentials (provisioner credentials).

```yaml
# frappe-postgres-provisioner.yaml
apiVersion: v1
kind: Secret
metadata:
  name: frappe-postgres-provisioner
  namespace: frappe-operator-system
stringData:
  # The default Percona postgres admin user
  user: postgres
  # Replace with the actual password generated by Percona
  password: your_secure_admin_password
```

Apply both:
```bash
kubectl apply -f frappe-postgres-cluster.yaml
kubectl apply -f frappe-postgres-provisioner.yaml
```

### Step 3.3: Deploying the Frappe Bench and Site

You can define PostgreSQL as the default provider at the `FrappeBench` level. All sites deployed to this bench will automatically inherit PostgreSQL settings.

```yaml
# bench-postgres.yaml
apiVersion: vyogo.tech/v1alpha1
kind: FrappeBench
metadata:
  name: postgres-bench
  namespace: frappe-operator-system
spec:
  framework:
    version: version-15
  dbConfig:
    provider: postgres
    mode: shared
    # postgresRef:
    #   name: custom-postgres-cluster # If you named your cluster something other than frappe-postgres
```

Deploy the site:

```yaml
# site-postgres.yaml
apiVersion: vyogo.tech/v1alpha1
kind: FrappeSite
metadata:
  name: example-postgres-site
  namespace: frappe-operator-system
spec:
  siteName: pg.example.com
  benchRef:
    name: postgres-bench
```

## 4. GitOps Data Safety & `deletionPolicy`

Data loss in production is unacceptable. By default, the `frappe-operator` prioritizes GitOps data safety above all else.

```yaml
spec:
  # Can be Retain or Delete
  deletionPolicy: Retain # Default
```

### `deletionPolicy: Retain` (The GitOps Safe Default)
If you delete the `FrappeSite` CR (e.g., via `kubectl delete`, an accidental ArgoCD sync, or a namespace teardown), the database, user, and credentials **will not be deleted** from the PostgreSQL server. 
- **What happens?**: The site's K8s resources (Ingress, Services) are removed, taking the site offline. 
- **Recovery**: Recreating the `FrappeSite` CR (with `skipInit: true`) instantly reconnects the site to the existing database without any data loss.

### `deletionPolicy: Delete` (Hard Purge)
If you are running CI/CD test environments and explicitly want the database to be destroyed when the site is deleted, set `deletionPolicy: Delete`.
- **What happens?**: Deleting the `FrappeSite` triggers a temporary K8s Job (`<site>-db-delete`) that connects to PostgreSQL and executes `DROP DATABASE` and `DROP ROLE`, completely and irreversibly purging the data.

## 5. Security Architecture (Strict Least Privilege)

The `frappe-operator` implements an impenetrable boundary between the Frappe application and the PostgreSQL infrastructure.

1. **Randomized Credentials**: Every shared site gets a randomly generated, unguessable database name (e.g., `_a1b2c3d4_pg_example_com`) and a securely generated 32-character password.
2. **Zero Superuser Privileges**: The generated user is strictly locked down. The operator provisions the role with `NOSUPERUSER`, `NOCREATEDB`, and `NOCREATEROLE`. The Frappe application cannot drop its own database or escalate privileges.
3. **Dedicated Provisioning Job Pattern**: The highly privileged `frappe-postgres-provisioner` credentials are **never** injected into the Frappe application pods (like `site-init-job` or web workers). Instead, the operator spins up a temporary, isolated K8s Job named `<site>-db-provision`. This job executes the sensitive `psql` creation statements and is immediately terminated, mitigating the blast radius if the Frappe application itself is ever compromised.
